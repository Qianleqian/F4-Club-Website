# 需求调查与每周记录模板

以下均为待填写模板和建议问题，目前没有开展真实访谈、问卷或观察。请保留实际证据及日期，区分受访者原话、小组解释和最终设计决定。

## SQIRO 调查清单

| 方法 | 建议操作 | 应保留的材料 |
|---|---|---|
| Sample Documents | 收集社团招新海报、报名表、活动通知样例 | 来源、获取时间、需要哪些字段 |
| Questionary | 问同学如何发现活动、最关心什么、是否需要提醒 | 问题、匿名结果、样本量、局限 |
| Interviews | 分别与学生、社团人员、老师和账号管理者沟通 | 实际对象角色、日期、问答摘要、待确认点 |
| Reading | 阅读原 spec、学校公开社团规则和课程材料 | 来源、与项目相关的规则或限制 |
| Observation | 观察一次现有报名或活动发布过程 | 实际步骤、耗时、问题、观察者解释 |

问卷不必收集学号、密码等无关信息。真实学校规则需要阅读后引用，不要假设基础版中的规则就是学校现行规定。

## 角色访谈提纲

学生：你通常从哪里发现活动？报名前需要知道什么？怎样确认报名成功？什么提醒形式有用？活动取消后希望怎样得知？

社团人员：发布时有哪些必填信息？谁有权修改？哪些内容最常变？是否需要筛选申请者？报名名单需要哪些信息？

老师：审核看哪些方面？驳回要不要给固定分类？已发布活动修改后怎样处理？公告和活动是否采用相同规则？

管理员：谁可以开通账号？角色如何确认？账号停用后已有报名如何保留？社团负责人换届如何交接？

## 建议 GitHub 协作约定

- main 保持可启动；按具体功能建分支，例如 feature/student-reminder。
- 一次 PR 对应一个可说明的需求或修复，写清验证方式。
- 合并前至少由另一位成员检查权限和异常流程，并运行测试。
- 修改公共请求/响应模型时先更新需求和接口文档，通知受影响成员。
- Wiki 可分为 Home、Requirements、Design、Testing、Meeting Notes、Portfolios，复用这些文档作为初稿。
