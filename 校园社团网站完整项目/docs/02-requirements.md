# 需求与验收清单

版本：0.1。来源标记：SPEC 为原 Mini Project 文档，TEAM 为用户给出的四角色方案，DESIGN 为本基础版的设计决定。以下清单是初稿，需要通过真实需求调查评审。

## 用户需求

- UR-01 参加活动的学生希望找到合适的社团活动，并知道自己是否报名成功。
- UR-02 社团工作人员希望提交活动、了解审核结果并管理参加人员。
- UR-03 老师希望在活动公开前检查信息，给出审核结论及意见。
- UR-04 管理员希望为用户分配正确的访问权限并停用无效账号。

## MoSCoW 的两个范围

本次基础版的 Must have 是登录和发布—审核—报名流程及账号管理；Should have 是更完整的边界测试及交互；Could have 是更多视觉优化。原 spec 明确包含的二维码、提醒、编辑、新闻公告应进入后续增量的必做清单，不能因为本次推迟就当作最终选做。

最终需求初稿：Must have 为 FR-01 至 FR-14；Should have 为 FR-15、审核历史和更完整的账号维护；Could have 为收藏、分类筛选、名单导出；Would have 为后续再讨论的统计看板等。此分级是建议，并非老师已经批准的结果。

## 四个最小用例

### UC-01 学生报名

前置条件：账号有效、角色为学生，活动已发布且未截止并有名额。

主流程：浏览列表，查看详情，点击报名，收到成功提示，打开我的报名查看记录。

异常流程：重复报名、截止、满员、活动取消均返回明确消息；失败操作不得新增记录。

验收：Given 可报名活动，When 学生确认报名，Then 名单和我的报名均新增同一条关系，人数增加 1。

### UC-02 社团提交活动

前置条件：账号有效、角色为社团工作人员，已关联社团。

主流程：填写必填字段，提交审核，在社团活动页看到待审核状态。

异常流程：非法日期、容量或空字段返回错误；不能通过请求指定其他社团。

验收：提交后学生公开列表不可见，老师待审核列表可见。

### UC-03 老师审核

前置条件：账号有效、角色为老师，活动待审核。

主流程：查看全部活动信息，填写意见，通过并发布或驳回。

异常流程：驳回不填写原因时拒绝；活动已经审核时拒绝重复审核。

验收：通过后公开列表可见，驳回后社团人员能看到驳回原因。

### UC-04 管理员维护账号

前置条件：账号有效、角色为管理员。

主流程：创建用户，指定角色，社团工作人员必须选择社团；必要时禁用账号。

异常流程：重复用户名或无效社团拒绝；不能禁用当前管理员自己。

验收：新账号能登录相应工作区；禁用后登录和已有 Session 下的受保护操作都被拒绝。

## 待确认问题

1. 学生与社团工作人员是否必须共用同一个多角色账号？v0.1 使用单角色账号。
2. 报名是否需要老师或组织者再次筛选？v0.1 报名成功即占名额，参加条件作为展示信息。
3. 发布后哪些修改需要重新审核？建议地点、时间、条件、内容等变更重新审核。
4. 降低容量时能否低于已报名人数？建议拒绝，避免隐式移除学生。
5. 提醒是站内提示、日历导出，还是关闭浏览器后也要通知？
6. 二维码手机扫码演示用哪台服务器和局域网？二维码链接必须能从手机访问。
